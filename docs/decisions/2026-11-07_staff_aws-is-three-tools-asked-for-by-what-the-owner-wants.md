- [staff] **Decision (2026-11-07): AWS is three tools an Odd asks for by what the owner wants, Secrets Manager (names only, and the office's keys), AWS read only, and AWS builder, on one office sign-in, and no Odd ever reads a secret value.** A value an Odd reads lands in its model's context, its transcript and the ledger, so values stay with the office and AWS's own permissions keep them from the Odds' roles. An Odd that cannot tell which the owner wants asks them first: use their secrets, read their data, or build in their account. The office signs in to the owner's IAM Identity Center once (a device sign-in with `sso:account:access`, never through `~/.aws`), keeps the tokens in the system's secret store until the access portal session ends, and each tool picks one role from that sign-in in one desk step. Secrets Manager's role is the office's: the office lists names to Odds itself and reads a value only to hand another tool its key (`fromAws`), so it needs no AWS tool for the Odd and nothing to install. Read only and builder run AWS's hosted MCP Server through `mcp-proxy-for-aws-cli` as their role, and connecting refuses a role that returns a secret value, dropping it unread. AWS read only's role is the boundary, so a Read only grant reaches all its tools. The site's guides (`/connectors/aws-*/`) give each role's policy: read only is AWS's ReadOnlyAccess, builder AWS's PowerUserAccess, which leaves out IAM, both with Denys on Secrets Manager values and Parameter Store. Other managers follow by kind: Google, Azure and Vault separate names from values in their own permissions, so they work the same way; 1Password, Bitwarden and Doppler cannot, so the office lists names itself; Cloudflare's Secrets Store never returns a value, so the office fetches nothing.
